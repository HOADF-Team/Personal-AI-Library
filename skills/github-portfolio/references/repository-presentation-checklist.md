# Чек-лист оформления репозитория

## Первые 30 секунд

README должен быстро отвечать:
1. Что это за проект?
2. Для кого он?
3. Что уже работает?
4. Как увидеть демонстрацию?
5. Как запустить?
6. Какие ограничения известны?

## Рекомендуемая структура README

- Название и краткое назначение.
- Ключевые возможности (только реализованные).
- Скриншоты или demo link.
- Требования и установка.
- Быстрый запуск и пример использования.
- Конфигурация через .env.example без секретов.
- Тесты и фактический статус.
- Ограничения/roadmap.
- Лицензия и благодарности.

## Перед публикацией

- Удалить секреты, персональные данные и приватные URL из истории/файлов.
- Если секрет уже опубликован, немедленно отозвать/ротировать его у провайдера. Удаление из Git не отменяет компрометацию и не инвалидирует credential.
- После ротации очистить текущие файлы и, по согласованной процедуре, историю Git, логи, artifacts, release assets и иные доступные копии. Учитывать, что forks, клоны, кеши и ранее скачанные данные могут остаться.
- Не вставлять сам секрет в issue, commit message, логи, отчёты или запрос к ИИ; передавать только тип credential и место обнаружения.
- Переписывание общей истории и force-push выполнять только после оценки последствий для collaborators, forks и CI/CD; при затрагивании чужой работы получить согласование.
- Проверить LICENSE: не указывать лицензию, если владелец её не выбрал.
- Проверить ссылки, изображения и инструкции с чистого окружения.
- Убедиться, что README не обещает функций, которых нет.
- Для Pages проверить base path и реальный опубликованный URL.
- Для релиза описать изменения и несовместимости.

## Портфолио

Показывать реальные доказательства: работающий demo, скриншот актуальной версии, тесты, понятный changelog. Не подменять отсутствие коммерческого опыта вымышленными кейсами и отзывами. Указывать личный вклад и использование сторонних компонентов честно.
