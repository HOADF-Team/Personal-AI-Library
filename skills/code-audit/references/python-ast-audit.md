# Методика аудита Python через AST

## Назначение и границы

AST позволяет проверить синтаксис и структуру Python без исполнения исследуемого кода. Это не доказывает корректность runtime-поведения и не обнаруживает все динамические импорты, обращения через reflection или ошибки данных.

## Последовательность

1. Зафиксировать корень проекта, версию Python, точку входа и команду запуска.
2. Исключить виртуальные окружения, кэши, сборки и каталоги зависимостей.
3. Разобрать каждый `.py` через `ast.parse`. Синтаксические ошибки записать отдельно; остальные файлы продолжать проверять.
4. Собрать определения функций, классов, импортов и вызовов. Учитывать, что AST не разрешает динамические имена и не доказывает существование вызываемого метода.
5. Сверить абсолютные импорты с файловой структурой. Скрипт считает корень проекта одним из import roots, сначала ищет локальный модуль (включая namespace package без `__init__.py`), затем стандартную библиотеку. Это помогает учитывать локальные модули, совпадающие по имени со stdlib. Относительные импорты, дополнительные `sys.path`, рабочая директория, import hooks и установленные внешние зависимости требуют отдельной проверки.
6. Просмотреть автоматические review-кандидаты:
   - `dynamic_code_candidate`: `eval`, `exec`, `compile`;
   - `process_execution_candidate`: прямые вызовы известных API `subprocess` и `os`;
   - `filesystem_mutation_candidate`: прямые вызовы известных API изменения/удаления файлов, `open(..., mode="w/a/x/+")`, `Path.open()` с буквальным режимом записи и распространённые методы `Path`, `os` и `shutil`;
   - `filesystem_access_candidate`: `os.open`, где флаги файлового дескриптора требуют ручной проверки;
   - `bare_except_candidate`: bare `except`;
   - `swallowed_exception_candidate`: `except Exception/BaseException` без обнаруженного повторного raise или логирования.
7. Считать эти находки только поводами для ручной проверки. Запись файлов, запуск процессов, динамический код и широкие обработчики могут быть штатной частью программы. Отсутствие находки не доказывает безопасность: aliases, переменные-экземпляры `Path`, динамические режимы/флаги, reflection, `getattr`, обёртки и динамические вызовы могут быть пропущены.
8. После статического анализа запускать только безопасные проверки в изолированном окружении: compileall, линтеры и тесты. Не запускать неизвестный entrypoint без оценки побочных эффектов.

## Интерпретация результатов

- **Подтверждено:** файл не парсится; импортируемый локальный модуль отсутствует при известной конфигурации запуска; тест воспроизводит ошибку.
- **Вероятно:** имя не найдено статическим поиском, но может создаваться динамически; импорт зависит от runtime path.
- **Требует проверки:** любой security review-кандидат. Сам по себе он не является доказанной ошибкой или уязвимостью.
- **Не проверено:** внешняя зависимость, удалённый сервис, секрет, база или биржевой API недоступны.

## Что обязательно записать в отчёт

Для каждого дефекта: путь, строка, правило, фрагмент/доказательство, влияние, уровень серьёзности и статус. Не смешивать найденные ошибки с рекомендациями. После исправления повторять только затронутую проверку и связанные сценарии.

## Безопасность

Не импортировать исследуемые модули ради introspection: импорт может выполнять произвольный код. AST-анализировать исходный текст. Не читать и не выводить значения секретов из `.env`; достаточно проверить наличие ключей конфигурации.
