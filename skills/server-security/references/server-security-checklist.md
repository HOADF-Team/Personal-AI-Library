# Server Security Checklist and Runbook

Рабочий чек-лист для Linux VPS и серверов. Это не готовый скрипт автоматического hardening. Сначала собери факты, затем согласуй изменения.

## 1. Контекст и границы

Зафиксируй владельца и разрешённый объём проверки, дистрибутив и версию, провайдера, назначение сервера, критичные данные, требования доступности, RPO/RTO, аварийный доступ, окно обслуживания и ответственного.

Не запускай тесты на чужих адресах и не выполняй эксплуатацию уязвимостей без разрешения владельца и согласованного scope.

## 2. Первичная read-only инвентаризация

Команды ниже предназначены для локальной диагностики. Вывод может содержать имена пользователей, адреса, версии и чувствительные сведения. Перед передачей отчёта редактируй их.

~~~bash
# OS and kernel
cat /etc/os-release
uname -a

# Listening sockets and network
sudo ss -tulpn
ip -brief address
ip route

# Accounts and privileges
getent passwd
getent group sudo
sudo -l

# Services
systemctl --type=service --state=running
systemctl --failed

# Storage
lsblk -f
findmnt
df -hT
df -ih

# Firewall state (read only)
sudo ufw status verbose
sudo nft list ruleset

# Debian/Ubuntu package updates
apt list --upgradable 2>/dev/null
~~~

Не передавай целиком вывод getent passwd, sudo -l, systemctl cat, journalctl, process command lines или конфигурационных файлов, пока не проверил их на секреты и персональные данные.

## 3. Контрольный список

### Учётные записи и SSH
- [ ] Нет общих административных аккаунтов.
- [ ] Удалены или заблокированы неиспользуемые учётные записи.
- [ ] Привилегии sudo ограничены необходимыми пользователями.
- [ ] SSH использует ключи/сертификаты и защищённые приватные ключи.
- [ ] Root login и password authentication оценены; отключение выполняется только после проверки альтернативного доступа.
- [ ] Удалены старые и скомпрометированные ключи.
- [ ] MFA включена там, где поддерживается.

### Сеть и сервисы
- [ ] Все открытые порты сопоставлены с конкретными сервисами и владельцами.
- [ ] БД, cache, панели администрирования и внутренние API не доступны публично без необходимости.
- [ ] Firewall и облачные security groups согласованы; IPv4 и IPv6 проверены отдельно.
- [ ] Исходящие соединения ограничены там, где это оправдано архитектурой.
- [ ] Ненужные сервисы и пакеты удаляются только после проверки зависимостей.

### Обновления и целостность
- [ ] ОС и компоненты поддерживаются производителями.
- [ ] Security updates устанавливаются по утверждённому графику.
- [ ] Перезапуски и обновления ядра планируются и контролируются.
- [ ] Сторонние репозитории и образы имеют понятное происхождение.
- [ ] Есть инвентаризация зависимостей и процесс обработки уязвимостей.

### Данные и криптография
- [ ] Классифицированы данные и определены места их хранения.
- [ ] Данные при передаче защищены актуальным TLS/SSH/VPN.
- [ ] Диски/тома, БД и резервные копии защищены шифрованием согласно модели угроз.
- [ ] Приватные ключи и ключи шифрования отделены от данных и имеют ограниченный доступ.
- [ ] Есть процедура ротации, отзыва и аварийного восстановления ключей.
- [ ] Пароли хранятся как стойкие salted password hashes, не как plaintext или обратимое шифрование.
- [ ] Сертификаты действительны, продлеваются и проверяются клиентами.
- [ ] В логах и дампах нет незащищённых секретов и лишних персональных данных.

### Резервное копирование
- [ ] Определены RPO/RTO и перечень данных для копирования.
- [ ] Есть независимая копия, которую нельзя удалить обычной учётной записью сервера.
- [ ] Копии зашифрованы, ключи хранятся отдельно.
- [ ] Срок хранения и доступ к копиям документированы.
- [ ] Выполняется реальное тестовое восстановление.
- [ ] Проверяются целостность и полнота восстановленных данных.

### Контейнеры и приложения
- [ ] Контейнеры не работают privileged без обоснования.
- [ ] Не используются лишние host mounts, host networking и Docker socket.
- [ ] Секреты не встроены в образы и слои сборки.
- [ ] Приложения работают с минимальными правами.
- [ ] Разделены учётные записи приложения, администратора и миграций БД.
- [ ] Защищены панели управления, API и внутренние endpoints.

### Логи, мониторинг и инциденты
- [ ] Время синхронизировано.
- [ ] Логи защищены от чтения и изменения посторонними.
- [ ] Есть оповещения о подозрительных входах, sudo и изменениях критичных конфигураций.
- [ ] Определены действия при утечке ключей, компрометации аккаунта и шифровальщике.
- [ ] Сохранение доказательств и восстановление проверены в учениях.

## 4. Шифрование: выбор по сценарию

| Сценарий | Что оценивать | Ограничение |
|---|---|---|
| Потеря диска/сервера | LUKS или шифрование тома облачным провайдером | Не защищает данные после разблокировки работающей системы |
| Резервные копии | Клиентское шифрование до отправки в хранилище | Потеря ключа может сделать копию невосстановимой |
| HTTPS/API | TLS 1.2/1.3 и проверка сертификатов | TLS до reverse proxy не шифрует автоматически proxy-to-backend |
| Пароли пользователей | Argon2id или поддерживаемая password-hashing схема | Хеширование не является обратимым шифрованием |
| Отдельные поля/файлы | Проверенная библиотека с аутентифицированным шифрованием | Не придумывать собственную криптографию |
| Ключи и секреты | KMS/secret manager или отдельное защищённое хранилище | Ключ нельзя хранить рядом с единственной копией данных |

Не выбирай параметры криптографии по случайной статье или устаревшему примеру. Используй поддерживаемые алгоритмы и конфигурации официальной платформы/библиотеки. Учитывай совместимость, ротацию, резервирование и доступность ключей.

## 5. Изменения с высоким риском блокировки доступа

Перед SSH/firewall/network changes:
1. Сохрани текущую конфигурацию в защищённом месте.
2. Убедись, что есть консоль провайдера или другой независимый способ доступа.
3. Проверь, что новое правило явно разрешает нужный административный адрес и порт.
4. Оставь текущую SSH-сессию открытой.
5. Применяй одно изменение за раз.
6. Открой вторую сессию и проверь вход.
7. Только после успеха закрывай старую сессию.
8. Зафиксируй процедуру отката.

Не выполняй ufw enable, массовую замену sshd_config, отключение паролей или изменение default route как универсальную команду без анализа действующих правил и доступа.

## 6. Резервное копирование и тест восстановления

Для каждого набора данных зафиксируй источник и метод backup, частоту и retention, шифрование и владельца ключа, место хранения и отдельные права, дату последнего успешного восстановления, фактическое время восстановления и проверку целостности.

Тестируй восстановление в отдельную среду, не поверх production. Сверяй контрольные суммы, количество объектов/строк, права доступа и возможность приложения прочитать восстановленные данные. Не заявляй, что backup надёжен, пока восстановление не проверено.

## 7. Реагирование на подозрение компрометации

1. Не удаляй логи и не очищай систему.
2. Запиши время, симптомы, затронутые учётные записи, сервисы и известные действия.
3. Сохрани доступные доказательства и ограничь доступ к ним.
4. По согласованному плану изолируй затронутый узел или сервис, сохраняя канал расследования.
5. С чистого доверенного устройства отзови/ротируй скомпрометированные ключи, токены и пароли; проверь связанные системы.
6. Определи точку первоначального доступа и масштаб компрометации.
7. Восстанавливай из доверенной копии после устранения первопричины.
8. Проверь систему после восстановления и документируй инцидент.

Если затронуты персональные данные или регулируемая информация, оцени обязательства по уведомлению с профильным специалистом. Не делай юридических выводов без сведений о юрисдикции и обстоятельствах.

## 8. Формат итогового отчёта

Для каждого замечания укажи:
- **ID / приоритет:** Critical, High, Medium, Low, Informational.
- **Актив и риск:** что может пострадать и каким образом.
- **Доказательство:** конкретный безопасно отредактированный факт.
- **Рекомендация:** минимальное обоснованное действие.
- **Риск внедрения:** простой, потеря доступа, несовместимость, потеря данных.
- **Проверка и откат:** как подтвердить результат и вернуть прежнее состояние.
- **Статус:** подтверждено, вероятно, не проверено, исправлено и повторно проверено.

Не присваивай Critical/High только по названию настройки. Учитывай экспозицию, доступность эксплуатации, ценность актива и последствия.
