# Telegram-бот: методика разработки и диагностики

## Сначала зафиксировать стек

Записать Python, библиотеку и точную версию (aiogram 2/3, python-telegram-bot и др.), режим polling/webhook, хранилище и способ запуска. Не смешивать примеры разных major-версий.

## Обработка обновлений

1. Разделить входной адаптер, бизнес-логику и слой хранения.
2. Обработчик должен проверять тип и полноту входных данных до обращения к БД/API.
3. Для callback query отвечать Telegram своевременно, даже если бизнес-операция выполняется дольше.
4. Команды, callback и текстовые сообщения проверять отдельно.
5. Для повторной доставки использовать update_id или собственный idempotency key там, где операция меняет состояние.
6. Для state-changing updates атомарно сохранять idempotency marker и durable queue/outbox item в одной транзакции. Не записывать update как обработанный до надёжного сохранения работы: сбой между этими шагами может безвозвратно потерять операцию при повторной доставке.
7. Для webhook подтверждать успешный приём только после durable acceptance, если контракт и используемый framework позволяют управлять подтверждением. Для polling не продвигать offset/подтверждение обновления до надёжного сохранения. Worker должен быть идемпотентным, поскольку очередь может доставить задачу повторно.
8. Для внешних API задавать connect/read timeout, ограниченные повторы с backoff и обработку 429/5xx.
9. Ограничивать параллелизм и учитывать rate limits платформы.

## Polling, webhook и срок хранения updates

- Webhook и getUpdates/polling взаимоисключающие режимы.
- Bot API хранит входящие updates не более 24 часов. Длительный простой может привести к потере событий; нужны мониторинг, оповещения и процедура восстановления.
- Требования к webhook (TLS, поддерживаемые порты, адресные диапазоны, IPv4/IPv6) могут меняться. Перед настройкой firewall сверяй текущую официальную webhook guide; не копируй IP allowlist из старых примеров без проверки.
- Используй документированный secret_token/механизм проверки webhook. Не полагайся только на секретный URL или неизвестный заголовок.

## Polling и webhook

- Не запускать одновременно два polling-процесса с одним токеном.
- Для webhook проверить HTTPS, публичную доступность endpoint, secret token, путь, регистрацию webhook и отсутствие конкурирующего polling.
- При запуске/остановке корректно закрывать сессию и фоновые задачи.
- Логи должны содержать update_id/корреляционный ID, но не токены и персональные данные.

## Права и безопасность

- Проверять user_id/chat_id и роль на серверной стороне для админских действий.
- Скрытая кнопка не является контролем доступа.
- Опасные действия подтверждать отдельным шагом; повторное нажатие не должно дублировать операцию.
- Токен держать в env/секрет-хранилище. При утечке отозвать его через BotFather.
- Не отправлять сообщения в реальные чаты и каналы без разрешения владельца.

## Минимальный набор тестов

- /start и неизвестная команда;
- корректный и некорректный callback;
- пользователь без прав;
- пустые/неожиданные данные;
- timeout внешнего API;
- повтор одного update;
- перезапуск процесса;
- недоступность БД.

## Диагностика

При ошибке фиксировать точный traceback, версию SDK, тип update и безопасный контекст. Не логировать весь объект update без фильтрации: в нём могут быть личные данные.
