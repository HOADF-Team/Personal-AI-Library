# Runbook интеграции API и webhook

## Контракт интеграции

Записать: владелец API, base URL, версия, auth scheme, методы, обязательные поля, формат ответа, pagination, rate limits, timeout и условия повторов. Секреты не включать в документ.

## API-клиент

- Отделить транспорт от бизнес-логики.
- Задать connect/read timeout.
- Проверять HTTP status и структуру ответа.
- Не считать любой 2xx гарантией корректных данных.
- Ограничить повторы; использовать exponential backoff с jitter для временных ошибок.
- Не повторять автоматически операции, которые могут создать платёж/заказ/сообщение, если нет idempotency key.
- Сохранять cursor/page token при пагинации и проверять, что цикл завершается.

## Webhook

1. Проверять подпись или секрет по официальному механизму платформы.
2. Валидировать схему payload.
3. Использовать уникальное ограничение на event ID для защиты от повторной доставки.
4. Атомарно сохранять входящее событие и задачу в durable queue/outbox (например, одной транзакцией БД). Не фиксировать статус «обработано» до надёжной постановки задачи: сбой между записью ID и enqueue иначе приведёт к потере события при повторной доставке.
5. Подтверждать webhook только после durable acceptance, если контракт платформы это допускает; долгую работу выполнять отдельным worker.
6. Обрабатывать события не по порядку, если платформа не гарантирует порядок.
7. Делать worker идемпотентным: повторная обработка задания не должна повторять внешний побочный эффект; где возможно, использовать downstream idempotency key.
8. Предусмотреть повторную доставку, retry с ограничением и dead-letter/error log.

## Секреты и доступ

Использовать env или защищённое хранилище. Не писать токены в URL, логи, traceback и репозиторий. Минимизировать scope ключей и регулярно проверять права.

## Тест-кейсы

Успех; пустой ответ; неверная схема; 401/403; 404; 429; 5xx; timeout; duplicate event; out-of-order event; expired token; pagination boundary; crash между приёмом события и enqueue; повтор worker после сбоя.

## Ввод в эксплуатацию

Сначала тестовая среда и ограниченный объём. До production проверить идемпотентность, логи, метрики, alerting и rollback. Не выполнять реальные побочные действия без разрешения.
