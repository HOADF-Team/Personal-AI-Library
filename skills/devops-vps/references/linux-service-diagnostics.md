# Linux VPS: read-only диагностика сервиса

## Сначала собрать факты

Выполнять команды по одной группе и сохранять результаты, не повторяя проверки без изменения условий.

```bash
date -Is
hostname
cat /etc/os-release
uptime
free -h
df -h
```

## systemd

```bash
systemctl status SERVICE --no-pager
systemctl cat SERVICE
journalctl -u SERVICE -n 100 --no-pager
```

Проверить: ExecStart, User, WorkingDirectory, EnvironmentFile (не печатать значения секретов), Restart policy и время последнего рестарта.

## Процессы и ресурсы

```bash
ps -eo pid,ppid,%cpu,%mem,rss,etime,cmd --sort=-rss | head -n 25
```

RSS показывается в KiB в типичных procps окружениях. Снимок — это момент времени, а не доказательство постоянной утечки памяти. Для динамики нужны повторные замеры через интервал, если это действительно требуется.

## Python-служба

Проверить:
- какой интерпретатор указан в ExecStart;
- существует ли venv и установлены ли зависимости именно в нём;
- cwd и права пользователя службы;
- пути к логам, БД и файлам относительно WorkingDirectory;
- переменные окружения по наличию, не раскрывая значения.

Не запускать второй экземпляр production-бота вручную, если он может подключиться к бирже или менять данные.

## Безопасные правила

- Не использовать `rm -rf`, очистку журналов/БД, kill процессов, restart и reboot в диагностическом режиме.
- Не выводить `.env`, приватные ключи и полные конфиги с секретами.
- Перед редактированием unit/config сохранить копию.
- После согласованного изменения проверять конкретный сервис, свежие логи и ожидаемый сценарий.
- На малом VPS учитывать RAM, swap, диск и лимиты процессов; не назначать новые тяжёлые службы без оценки ресурсов.

## Краткий отчёт

Команда → наблюдение → что это подтверждает → чего не доказывает → следующий минимальный шаг.
