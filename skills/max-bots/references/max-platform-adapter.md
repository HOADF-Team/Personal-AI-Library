# MAX: безопасная схема интеграции

## Важное ограничение

Не считать MAX совместимым с Telegram Bot API. Методы, endpoint, типы кнопок, payload, авторизация, события и лимиты должны подтверждаться текущей официальной документацией MAX. Этот документ задаёт архитектурный подход, а не заменяет справочник API.

## Текущие checkpoints официальной документации (проверено 2026-11-27)

Эти сведения помогают обнаружить устаревшие примеры, но перед каждой реализацией их нужно сверять с текущей документацией и changelog:

- **Eligibility:** текущая документация указывает, что создание ботов доступно юрлицам, ИП и самозанятым — резидентам РФ. Проверить право владельца до оценки проекта и обещания запуска.
- **API host/auth:** документация указывает домен `platform-api2.max.ru`; токен передаётся в заголовке `Authorization`, а не в query-параметрах.
- **Webhook transport:** с 25 мая 2026 документация указывает прекращение поддержки HTTP и самоподписных сертификатов для webhook. Использовать HTTPS и доверенный сертификат; не отключать TLS-проверку как обход проблемы.
- **Response handling:** проверять и HTTP status, и JSON body. Для некоторых методов HTTP 200 может сопровождаться `success: false` и кодом ошибки.
- **Production delivery:** официальная инструкция рекомендует webhook для production; long polling ограничен по скорости и сроку хранения событий. Точный retry window и delivery limits проверять в актуальной документации.

## Разделение слоёв

Рекомендуемая структура:

- `domain/` — независимые правила и сценарии приложения;
- `platforms/max_client.py` — HTTP/SDK адаптер MAX;
- `platforms/max_handlers.py` — преобразование событий MAX в команды приложения;
- `storage/` — работа с БД;
- `config.py` — настройки без значений секретов в git.

Бизнес-логика не должна напрямую зависеть от формата update конкретной платформы. Если одновременно нужны Telegram и MAX, у каждой платформы свой адаптер, а общий слой используется только для действительно одинаковых сценариев.

## Перед реализацией конкретного метода

1. Открыть официальный раздел документации для метода.
2. Зафиксировать URL, HTTP method, auth scheme, обязательные поля, формат ответа и версию/дату проверки.
3. Проверить лимиты, timeout, ошибки и правила повторной отправки.
4. Сверить пример на тестовом боте.
5. Добавить contract test для сериализации запроса и разбора ответа.

## Авторизация действий

- Проверять права на сервере при каждом state-changing callback/action.
- Использовать идентификатор пользователя и роли, полученные/проверенные по документированному механизму платформы и данным приложения.
- Не считать наличие кнопки, скрытие элемента интерфейса или присланные клиентом поля подтверждением права.
- Не предполагать названия полей MAX или способ проверки подписи: сначала подтвердить их официальной документацией.

## Надёжность webhook и повторной доставки

- Секреты только в env/секрет-хранилище.
- Проверять подпись, secret header или иной механизм webhook строго по документированной схеме MAX; не копировать схему Telegram.
- Таймауты обязательны.
- Повторять только временные ошибки и только безопасные/idempotent операции.
- Сохранять ID входящего события для защиты от повторной обработки.
- Для state-changing событий атомарно сохранять idempotency marker и durable queue/outbox item в одной транзакции. Если транзакция не завершилась, не должно остаться ни маркера обработанного события, ни задания.
- Подтверждать webhook только после durable acceptance, если API/framework позволяют управлять моментом ответа. Если платформа требует другой порядок, явно описать этот контракт и обеспечить восстановление без потери события.
- Worker должен быть идемпотентным: повторная доставка задания не должна повторять бизнес-эффект.
- Не предполагать типы кнопок или callback payload без документации.

## Contract tests

Минимальный набор локальных проверок:
- корректный и некорректный формат входящего события;
- дубликат одного event ID;
- сбой до commit и повторная доставка;
- повторный запуск worker без повторного бизнес-эффекта;
- отказ в state-changing действии для пользователя без нужной роли;
- отклонение неверной webhook-аутентификации по фактическому документированному механизму.

Если точный API-контракт MAX не предоставлен, тестировать только абстрактный адаптерный контракт и явно отметить, что реальная сериализация/подпись не проверена.

## Что Codex должен сообщить

Если официальный API не подтверждает нужную функцию, обозначить это как неизвестное/неподдержанное. Не генерировать вымышленные endpoint, поля и SDK методы.
