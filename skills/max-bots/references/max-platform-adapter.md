# MAX: безопасная схема интеграции

## Важное ограничение

Не считать MAX совместимым с Telegram Bot API. Методы, endpoint, типы кнопок, payload, авторизация, события и лимиты должны подтверждаться текущей официальной документацией MAX. Этот документ задаёт архитектурный подход, а не заменяет справочник API.

## Разделение слоёв

Рекомендуемая структура:

- `domain/` — независимые правила и сценарии приложения;
- `platforms/max_client.py` — HTTP/SDK адаптер MAX;
- `platforms/max_handlers.py` — преобразование событий MAX в команды приложения;
- `storage/` — работа с БД;
- `config.py` — настройки без значений секретов в git.

Бизнес-логика не должна напрямую зависеть от формата update конкретной платформы. Если одновременно нужны Telegram и MAX, у каждой платформы свой адаптер, а общий слой используется только для действительно одинаковых сценариев.

## Перед реализацией конкретного метода

1. Открыть официальный раздел документации для метода.
2. Зафиксировать URL, HTTP method, auth scheme, обязательные поля, формат ответа и версию/дату проверки.
3. Проверить лимиты, timeout, ошибки и правила повторной отправки.
4. Сверить пример на тестовом боте.
5. Добавить contract test для сериализации запроса и разбора ответа.

## Надёжность

- Секреты только в env/секрет-хранилище.
- Таймауты обязательны.
- Повторять только временные ошибки и только безопасные/idempotent операции.
- Для webhook проверить подпись/секрет по документированному механизму.
- Сохранять ID входящего события для защиты от повторной обработки.
- Не предполагать типы кнопок или callback payload без документации.

## Что Codex должен сообщить

Если официальный API не подтверждает нужную функцию, обозначить это как неизвестное/неподдержанное. Не генерировать вымышленные endpoint, поля и SDK методы.
