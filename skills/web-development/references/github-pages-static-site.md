# GitHub Pages: структура и публикация статического сайта

## Ограничения платформы

GitHub Pages отдаёт статические файлы. HTML/CSS/JS работают в браузере; секреты, приватные API-ключи и серверные операции нельзя помещать в клиентский код. Для защищённой логики нужен отдельный backend или serverless-сервис.

## Перед изменениями

1. Найти фактическую публикационную ветку/папку и workflow.
2. Проверить `index.html`, связанные страницы, CSS, JS, assets и относительные пути.
3. Проверить, используется ли сборщик (Vite и т.п.) или сайт публикуется напрямую.
4. Не менять существующую архитектуру ради небольшого исправления.

## Пути и маршрутизация

- Для project site URL обычно содержит имя репозитория в пути. Не предполагать корень домена.
- Проверять пути к CSS, JS, изображениям и ссылкам на вложенных страницах.
- Не использовать абсолютный путь от `/` без проверки base path.
- Учитывать регистр имён файлов: Linux hosting чувствителен к регистру.
- Для SPA проверить fallback/404 поведение; GitHub Pages не предоставляет произвольную серверную маршрутизацию.

## Адаптивность и качество

Проверить минимум узкий мобильный экран и desktop:
- отсутствие горизонтальной прокрутки;
- читаемость и размер интерактивных элементов;
- меню и модальные окна;
- формы, пустые состояния и сообщения об ошибках;
- клавиатурный фокус и семантические элементы.

## Перед публикацией

1. Проверить локальную сборку, если она есть.
2. Убедиться, что артефакты сборки попадают в опубликованную папку.
3. Проверить workflow и его логи, а не только факт push.
4. Открыть опубликованный URL и проверить затронутый сценарий.
5. Если Pages ещё не обновился, отличать задержку публикации от ошибки кода.

## Секреты и API

Публичный JavaScript виден всем. Запросы к стороннему API допустимы только если API предназначен для публичного доступа и не требует секретного ключа. CORS нельзя надёжно «исправить» клиентским обходом; нужен корректный серверный endpoint.
